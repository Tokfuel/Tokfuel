# アプリ関連を App/ 配下に集約する

[English](./README.md)

## Decision（決定事項）

> アーキテクチャやソリューションの意思決定の内容

### 決定事項

アプリ本体・UT/IT・テスト設計・通しテストの置き場を、次の木に固定する。

- `App/Tokfuel/` … アプリ本体（旧 `Tokfuel/Sources`）
- `App/Tests/` … UT / IT（旧 `Tokfuel/Tests`）
- `App/TestDocs/` … シナリオ設計
- `App/E2E/` … 通しテスト

Site や SPM モジュール分割（#109）は対象外とする。挙動は変えず、配置と参照の更新だけとする。

単に移すだけでなくディレクトリ名も変える。`Sources` / `Tests` のままだと「リポジトリ全体のソース」にも読め、スコープが曖昧になる。アプリ本体だと分かる名前（`App/Tokfuel`）に寄せ、TestDocs / E2E を同じ親の下に置くことで、製品コードの木と Site / Docs / Scripts などの運営物を分ける。

### 比較・検討内容の要約

現状維持では TestDocs / E2E の置き場が後からばらける。トップレベルに兄弟として並べると入口は増えるが、Site などと階層が混ざる。`App/` 配下に集約すればアプリ関連の親が一つになるため、案3を採用した。

## Context（経緯・背景情報）

> この意思決定が行われる背景、問題点、目的など

### 背景

アプリ本体は `Tokfuel/Sources`、単体・結合テストは `Tokfuel/Tests` にあり、SPM の単一 target から参照していた。シナリオ設計（TestDocs）と通しテスト（E2E）をリポジトリに載せる必要が出てきた（#134）。これらをトップレベルや別ツリーに置くと、アプリ周りの入口が増えていく。

### 課題

1. **置き場がばらける**
   - 本体・UT/IT・設計表・E2E が別階層になると、コントリビュータが「どこを触るか」を毎回探し、無関係な変更が同じ PR に混ざりやすい。
2. **後続の箱が増やせない**
   - TestDocs / E2E 用の置き場を先に決めないと、後から別慣習が生え、#109 のモジュール分割とも噛み合わせにくい。
3. **名前がスコープを表さない**
   - ルートや `Tokfuel/` 直下の `Sources` は「リポジトリ全体のソース」にも読める。アプリ製品の木だと一目で分かる親が欲しい。

### 目的

- アプリ関連の探索入口を `App/` に一つにする
- TestDocs / E2E を同じ木の下に置けるようにする
- 挙動は変えず、配置方針だけを固定する

## Consideration（比較・検討内容）

> 他に検討した選択肢や検討した内容

### 比較対象

| 案 | ソリューション | 概要 |
|----|----------------|------|
| 案1 | **現状維持** | `Tokfuel/Sources` + `Tokfuel/Tests` のまま。TestDocs / E2E は都度別場所 |
| 案2 | **トップレベルに並べる** | ルートに `Tokfuel/`（または `Sources/`）・`Tests/`・`TestDocs/`・`E2E/` を兄弟として置く |
| 案3 | **`App/` 配下に集約** | `App/Tokfuel` / `App/Tests` / `App/TestDocs` / `App/E2E` |

### 比較表

| 評価項目 | 案1 現状維持 | 案2 トップレベル | 案3 `App/` 集約 |
|----------|--------------|------------------|-----------------|
| 探索しやすさ | × アプリ箱が増えるたびに入口が増える | △ 兄弟は揃うが Site / Docs と同じ階層で混ざる | ◎ アプリ関連の親が一つ |
| TestDocs / E2E の伸ばしやすさ | × 置き場の慣習が後付けになる | ○ 並べられるが親が共有されない | ◎ 同じ `App/` の下に足せる |
| 移行コスト | ◎ 変更不要 | ○ パス更新は必要だが浅い | ○ パス更新は必要。挙動変更は不要 |
| #109 との両立 | △ 「アプリの中」の境界が薄い | △ ルートが製品と運営で混在 | ○ モジュール分割の土台を `App/` に限定しやすい |
| Site への影響 | ◎ 触らない | ◎ 触らない（ただし階層上は隣） | ◎ 対象外のまま外に置ける |

### 総合評価

| 案 | 総合評価 | 判定 |
|----|----------|------|
| 案1: 現状維持 | ばらけ方と後続箱の課題が残る | **不採用** |
| 案2: トップレベル | 入口は増えるが、運営物と製品箱が同じ階層で混ざる | **不採用** |
| 案3: `App/` 集約 | アプリ関連だけ親が一つ。Site は外に置いたまま | **採用** |

## Consequences（結果）

> 予期される結果。意思決定がシステムやプロジェクトに与える影響

### 期待される効果

1. アプリ関連の探索入口が `App/` に一つになり、TestDocs / E2E を同じ木の下に足せる
2. Site / Docs / Scripts などリポジトリ運営物と、製品コードの境界がディレクトリで分かる
3. #109 のモジュール分割を進めるときも、「アプリの中」の話として範囲を切りやすい

### 技術的リスクと対策

| リスク | 内容 | 対策 |
|--------|------|------|
| パス追従漏れ | `Package.swift`・CI・スクリプト・文書が旧パスのまま残る | #134 の実装で一括更新。`swift test` / `swift build -c release` で確認 |
| 外部リンク切れ | 古いパスを指すブックマークやフォーク | README / AGENTS を新パスに更新。挙動は変えないので実行時影響はなし |
| 範囲の膨張 | 版正本やトップレベル改名まで同じ決定に含めてしまう | 本 ADR は **App/ 集約だけ**。それ以外は別決定 |
